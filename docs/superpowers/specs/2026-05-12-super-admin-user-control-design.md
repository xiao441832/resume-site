# 超级管理员用户管控设计说明

## 一、目标定位

本次改造把系统账号明确拆成两类：超级管理员和普通用户。超级管理员是网站系统管理者，不作为公开简历用户参与展示；普通用户是简历发布者，只能维护自己的简历内容和留言。

改造后系统仍然保持 Python、Flask、Jinja2、Bootstrap 5、PyMySQL、MySQL 8.0、Nginx、Gunicorn、systemd 的服务端渲染架构，不引入前后端分离框架。

## 二、账号类型

系统只保留两种账号类型：

- `super_admin`：超级管理员账号，用于登录系统后台 `/admin`。
- `user`：普通用户账号，用于登录个人后台 `/dashboard`。

现有 `admin` 角色不再作为长期角色保留。部署迁移时，当前管理员账号升级为 `super_admin`，后续新注册用户全部为 `user`。

## 三、超级管理员能力

超级管理员后台需要具备网站平台常见的系统管理能力：

- 查看系统概览：用户总数、正常用户数、封禁用户数、公开简历数、被封禁简历数、留言数、最近注册用户、最近留言。
- 查看用户列表：支持按用户名、邮箱、昵称和账号状态筛选。
- 查看用户详情：展示账号信息、简历公开状态、发布权限、简历数据统计、最近留言。
- 封禁账号：被封禁用户不能登录，公开简历也不再展示。
- 解封账号：恢复用户登录能力，但是否公开简历仍由发布权限和简历状态共同决定。
- 禁止发布：用户可以登录和编辑资料，但不能把简历公开到前台。
- 恢复发布：用户重新获得公开简历的能力。
- 封禁公开简历：只隐藏该用户的公开简历，不影响账号登录。
- 恢复公开简历：解除系统层面的公开简历封禁。
- 管理全站留言：继续保留现有全站留言查看、状态处理和删除能力。
- 管理站点设置：继续保留站点标题、SEO 描述、备案信息、留言开关等配置。

超级管理员不能被普通用户操作。第一版不做“删除用户”和“重置用户密码”，避免误删数据和扩大功能范围。

## 四、普通用户限制

普通用户仍然使用 `/dashboard` 维护自己的简历内容。新增限制如下：

- 被封禁账号不能登录。
- 被禁止发布的用户可以登录和编辑资料，但保存个人信息时不能把“前台展示”设置为开启。
- 公开简历被超级管理员封禁时，用户仍可登录和编辑资料，但前台 `/u/<username>` 返回 404。
- 用户后台个人信息页需要提示当前账号是否被禁止发布、公开简历是否被封禁以及对应原因。
- 普通用户不能访问 `/admin` 下的任何页面。

## 五、公开展示规则

首页公开简历列表和用户公开简历页必须同时满足以下条件才展示：

- 用户角色为 `user`。
- 用户账号 `is_active = 1`。
- 用户允许发布 `can_publish = 1`。
- 个人资料 `profile.is_active = 1`。
- 公开简历未被系统封禁 `profile.is_public_blocked = 0`。

留言提交使用同一套公开用户查询规则。被封禁、禁止发布、隐藏简历或公开简历被封禁的用户都不能收到前台公开留言。

## 六、数据库设计

`users` 表需要调整：

```sql
role ENUM('super_admin','user') NOT NULL DEFAULT 'user'
can_publish TINYINT(1) NOT NULL DEFAULT 1
ban_reason VARCHAR(255) NULL
publish_ban_reason VARCHAR(255) NULL
```

字段含义：

- `role`：账号类型，只区分超级管理员和普通用户。
- `is_active`：账号是否启用，关闭后不能登录。
- `can_publish`：是否允许发布公开简历。
- `ban_reason`：账号封禁原因。
- `publish_ban_reason`：禁止发布原因。

`profile` 表需要增加：

```sql
is_public_blocked TINYINT(1) NOT NULL DEFAULT 0
public_block_reason VARCHAR(255) NULL
```

字段含义：

- `is_public_blocked`：是否被超级管理员封禁公开简历。
- `public_block_reason`：公开简历封禁原因。

需要新增迁移 SQL，兼容当前已有的 `admin` 角色，把它升级为 `super_admin`。线上数据库数据没有保留价值时，也可以直接执行新版 `schema.sql` 重建。

## 七、路由设计

认证路由继续使用统一登录：

```text
/auth/login
/auth/register
/auth/logout
```

登录跳转规则：

- `super_admin` 登录成功后进入 `/admin`。
- `user` 登录成功后进入 `/dashboard`。
- 被封禁账号登录时停留在登录页并提示账号已被禁用。

超级管理员新增路由：

```text
/admin/users
/admin/users/<user_id>
/admin/users/<user_id>/account-status
/admin/users/<user_id>/publish-status
/admin/users/<user_id>/resume-status
```

这些路由都必须限制为 `super_admin` 访问。

## 八、页面设计

超级管理员后台侧边栏新增“用户管理”。系统概览页增强统计卡片和最近数据：

- 用户总数
- 正常用户
- 已封禁用户
- 公开简历
- 被封禁简历
- 留言总数
- 未读留言

用户管理列表展示：

- 用户名
- 昵称
- 邮箱
- 账号状态
- 发布权限
- 公开简历状态
- 注册时间
- 最近登录时间
- 操作入口

用户详情页展示账号资料和三类操作表单：

- 账号封禁/解封
- 禁止发布/允许发布
- 封禁公开简历/恢复公开简历

所有操作表单都要使用 CSRF 防护，并提供原因输入框。解封或恢复时清空对应原因。

## 九、后端权限设计

当前 `admin_required` 需要调整为只允许 `super_admin`。为了让代码语义更清楚，建议增加：

```text
super_admin_required
is_super_admin
```

普通用户后台继续通过 `login_required` 保护，并在进入 `/admin` 时返回 403。

资源管理中当前“管理员区域可跨用户查看”的逻辑需要改为“超级管理员区域可跨用户查看”。普通用户区域仍然强制按当前用户过滤。

## 十、错误处理和提示

用户操作失败时使用中文提示：

- 用户不存在。
- 不能操作超级管理员账号。
- 账号已封禁，无法登录。
- 当前账号已被禁止发布，不能公开简历。
- 公开简历已被系统封禁。

后台操作成功时使用中文提示：

- 账号状态已更新。
- 发布权限已更新。
- 公开简历状态已更新。

## 十一、测试策略

需要补充以下测试：

- `super_admin` 登录后跳转 `/admin`。
- 普通用户登录后跳转 `/dashboard`。
- 旧 `admin` 角色兼容或迁移为 `super_admin`。
- 被封禁用户不能登录。
- 普通用户不能访问 `/admin/users`。
- 超级管理员可以访问用户管理列表。
- 超级管理员可以封禁和解封普通用户。
- 超级管理员可以禁止和恢复发布权限。
- 超级管理员可以封禁和恢复公开简历。
- 被禁止发布的用户不能把个人资料设置为公开。
- 被封禁公开简历的用户不会出现在首页列表。
- 被封禁公开简历的用户公开页返回 404。
- 数据库结构包含新增字段和新的角色枚举。

## 十二、部署影响

部署时需要更新代码、执行数据库迁移、重启 Gunicorn 服务。当前线上数据库没有保留价值时，可以直接重建表结构并执行初始化数据。

默认初始化数据中应创建：

- 一个超级管理员账号。
- 一个普通演示用户账号。

线上部署完成后需要验证：

- 超级管理员能登录后台并看到用户管理。
- 普通用户能登录个人后台。
- 封禁账号后该账号不能登录。
- 禁止发布后该账号不能公开简历。
- 封禁公开简历后前台不可访问。
- 首页、公开简历页、留言提交、后台保存都没有 500 或 502。
